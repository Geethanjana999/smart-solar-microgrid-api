# Smart Solar Microgrid Trading System API

ASP.NET Core Web API using MongoDB. All business rules are in services; controllers expose REST endpoints only.

## Setup and run

1. Install/start MongoDB locally, or use MongoDB Atlas.
2. Copy `appsettings.example.json` to the untracked `appsettings.json`, or set `MongoDb__ConnectionString`, `MongoDb__DatabaseName`, and `Jwt__Key` environment variables. Set `Jwt__Key` to a long secret outside development.
3. Run `dotnet restore` then `dotnet run` from this project directory.
4. Browse to `/swagger` (normally `https://localhost:xxxx/swagger`).

The startup seed creates Mongo indexes and test data. Test password for all accounts is `Password123!`: `backoffice` (Backoffice), `operator` (GridOperator), and `199012345678` (Prosumer).

## Project structure

`Configuration/` options and roles, `Models/` MongoDB documents, `DTOs/` request/response types (one per file), `Data/` Mongo context and seeder, `Services/Interfaces/` + `Services/` business logic, `Controllers/` thin REST endpoints, `Middleware/`, `Extensions/`, `HealthChecks/`.

## Endpoint groups

| Area | Endpoints | Roles |
|---|---|---|
| Auth | `POST /api/auth/login` | anonymous |
| Web users | `GET/POST/PUT /api/users` (Backoffice / GridOperator accounts only) | Backoffice |
| Prosumer self-service | `POST /api/prosumers/register` (account stays pending), `GET/PUT /api/prosumers/me`, `POST /api/prosumers/me/deactivation-request` | anonymous / Prosumer |
| Prosumer management | `GET /api/prosumers?status=pending\|active\|inactive\|deactivation-requested`, `POST`, `PUT /{nic}`, `POST /{nic}/activate`, `POST /{nic}/deactivate` | Backoffice (`GET /{nic}` also operator) |
| Stations | `GET /api/stations`, `GET /api/stations/nearby?latitude=&longitude=&radiusKm=` | anonymous |
| | `POST`, `PUT /{id}`, `DELETE /{id}` | Backoffice |
| | `PUT /api/stations/{id}/battery-slots` | Backoffice, GridOperator |
| Slots | `GET /api/slots?stationId=` (public), `POST/PUT/DELETE` | Backoffice |
| Prosumer bookings | `GET /api/reservations` (`state, from, to, stationId, search`), `/current`, `/pending`, `/history`, `POST`, `PUT /{id}`, `DELETE /{id}` | Prosumer |
| Staff bookings | `GET/POST /api/staff/reservations`, `PUT/DELETE /{id}`, `POST /{id}/approve` | Backoffice, GridOperator |
| Operator | `POST /api/operator/verify-qr`, `POST /api/operator/reservations/{id}/finalize` | GridOperator, Backoffice |
| Dashboard | `GET /api/dashboard` (own counts for prosumers, system-wide for staff) | any signed-in role |
| Health | `GET /health` (pings MongoDB) | anonymous |

Use `Authorization: Bearer <token>` after login.

## Business rules (enforced in the services)

- Self-registered prosumers cannot log in until Backoffice activates them; only Backoffice can reactivate a deactivated account. A prosumer with open reservations cannot be deactivated.
- Bookings must start within the next 7 days; updates and cancellations need at least 12 hours before the slot starts.
- A new reservation is `Pending`. Staff approve it (`Confirmed`); only then is `qrToken` returned. The operator verifies the token (approved reservations only) and finalises it (`Completed`).
- A station or slot with pending/confirmed reservations cannot be deactivated/deleted.
- Slot energy changes use optimistic concurrency so two simultaneous bookings cannot oversell a slot.

## IIS deployment

Install the .NET Hosting Bundle on the server. Publish with `dotnet publish -c Release -o ./publish`; create an IIS site pointing at `publish`, use an app pool with **No Managed Code**, and set the MongoDB/JWT values as IIS environment variables. Ensure MongoDB/Atlas is reachable from the server.

After publishing, open `/swagger` and `/health` on the IIS site to confirm the API and MongoDB connection. `web.config` is generated by `dotnet publish` (in-process hosting). Do not zip the published `appsettings.json` into the submission, as it holds your real connection string.
